# DB08 — Kapasitas dan performa penyimpanan

Pengukuran lokal memakai Windows 10 x64, Intel Core i5‑10400 (12 logical
CPU), RAM 15,83 GiB, Node 24.15.0, dan Chromium 159.0.8154.6 tanpa throttling.
Baseline memakai kode aplikasi pada `01bae63`. Pengukuran sesudahnya memakai
fixture dan harness yang sama dengan optimasi validasi JSON.
[Sampel waktu, memori, dan kuota](db08.json).

## Fixture dan metode

| Fixture | Bab × kata per bab | Vektor adegan | Sesi × pesan | Snapshot di satu bab | PNG 1 × 1 px | JSON lengkap | Estimasi penggunaan origin |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Kecil | 10 × 1.000 | 100 | 5 × 20 | 5 | 1 | 0,13 MiB | 0,14 MiB |
| Sedang | 100 × 2.000 | 1.000 | 30 × 60 | 30 | 2 | 2,31 MiB | 0,71 MiB |
| Besar | 500 × 5.000 | 10.000 | 100 × 100 | 120 | 4 | 20,71 MiB | 5,98 MiB |

Data sintetis masuk ke IndexedDB native pada context browser terisolasi.
Harness memakai prosa ASCII berulang dan pesan dengan identitas unik.
PNG kecil menguji round-trip aset dengan biaya minimum. Arsip bisa jauh
berbeda pada naskah dengan banyak kutip, Unicode, atau aset besar.
`navigator.storage.estimate()` diambil setelah seed sebelum pencadangan.
Kuota yang dilaporkan sekitar 10 GiB pada profil ini, sedangkan batas
arsip tetap mengikuti [kontrak cadangan](../../backup-format.md#batas-input).
Estimasi platform tidak menetapkan kapasitas maksimum proyek.

Lima sampel setelah pemanasan. Simpan mengukur transaksi melalui
`saveChapterContent` dengan perbandingan isi awal. Waktu debounce, rendering
TipTap, dan kerja UI berada di luar sampel. Pencarian mengukur ranking
semantik 384 dimensi melalui jalur F23 dengan vektor siap pakai.
Chat mengukur resume Workshop, snapshot mengukur pembacaan riwayat, dan
serialisasi membuat JSON berindentasi seperti unduhan manual. Restore
mencakup validasi, snapshot pengaman, dan transaksi penggantian data.
Harness memeriksa seluruh record ekspor, referensi, gambar, dan checksum
setelah restore pada setiap ukuran.

## Hasil sebelum dan sesudah

Median milidetik. Setiap sel menunjukkan baseline → hasil optimasi.

| Operasi | Kecil | Sedang | Besar |
| --- | ---: | ---: | ---: |
| Simpan editor (commit) | 1,7 → 1,4 | 1,4 → 1,5 | 2,4 → 2,4 |
| Daftar bab | 0,9 → 0,8 | 2,1 → 2,0 | 8,0 → 8,6 |
| Pencarian adegan | 6,2 → 5,6 | 44,2 → 44,1 | 400,6 → 397,9 |
| Buka kembali chat Workshop | 1,4 → 1,0 | 7,1 → 7,1 | 32,8 → 32,6 |
| Daftar snapshot | 1,2 → 0,8 | 3,8 → 3,8 | 20,1 → 19,9 |
| Kumpulkan ekspor | 5,5 → 4,8 | 40,7 → 40,3 | 311,5 → 310,3 |
| Validasi dan serialisasi ekspor | 2,0 → 1,4 | 24,0 → 15,5 | **174,9 → 121,5** |
| Verifikasi checksum sebelum restore | 2,3 → 1,8 | 33,3 → 23,8 | 260,5 → 196,1 |
| Restore penuh | 19,5 → 17,1 | 172,2 → 148,4 | 1.315,4 → 1.141,5 |

Target batch untuk fixture besar ditetapkan dari baseline sebelum perubahan.
Median serialisasi harus turun minimal 20% (≤139,9 ms) dan tambahan backing
storage tersampel minimal 50% (≤9,83 MiB). Hasil 121,5 ms dan 0 MiB memenuhi
keduanya. Optimasi menghitung byte string ASCII tanpa karakter escape dari
panjang string ditambah dua tanda kutip. Input non-ASCII, karakter kontrol,
kutip, dan backslash memakai penghitungan UTF-8 atas hasil `JSON.stringify`.
Tes mencakup penerimaan tepat di batas dan penolakan satu byte di bawahnya.

### Memori di luar worker

CDP `Runtime.getHeapUsage` mengambil sampel tiap sekitar 20 ms pada main
thread. Tabel menunjukkan median tambahan puncak dari tiga probe per operasi
di fixture besar. Forced GC berjalan sebelum probe. Heap awal sudah mencakup
payload fixture yang dipegang harness. Hasil bisa melewatkan puncak singkat dan
mencerminkan jadwal GC V8. Backing storage mencakup buffer eksternal V8.

| Operasi | Heap JS (MiB) | Backing storage (MiB) |
| --- | ---: | ---: |
| Serialisasi ekspor | 23,75 → 21,13 | 19,65 → 0,00 |
| Verifikasi checksum | 62,75 → 60,13 | 39,69 → 20,04 |
| Restore penuh | 107,54 → 142,55 | 120,79 → 81,49 |

Pada restore, backing storage turun dan heap JS tersampel naik. Data ini
belum membuktikan penurunan puncak memori keseluruhan restore. CDP tidak
mengukur total memori proses, memori storage native, atau editor aktif.

## Keputusan berdasarkan pengukuran

| Kandidat | Keputusan batch |
| --- | --- |
| Pagination daftar bab atau snapshot | Daftar bab sudah memakai covering index dan memerlukan sekitar 9 ms untuk 500 bab. Pembacaan 120 snapshot sekitar 20 ms. Pertahankan alur yang terukur. |
| Indeks pencarian tambahan | Pencarian besar memerlukan sekitar 400 ms pada ranking exact dengan pembacaan batch. Pengukuran ini belum menunjukkan indeks baru akan mengurangi biaya ranking. |
| Pemisahan pesan chat | Resume Workshop pada 100 sesi dengan total 10.000 pesan memerlukan sekitar 33 ms. Pemisahan tabel ditunda sampai ada pengukuran riwayat yang lebih besar atau pemuatan daftar chat di UI. |
| Retensi cache | Regenerasi dan pembersihan cache mengikuti kebijakan tabel. Estimasi origin pada fixture ini belum menunjukkan tekanan kuota untuk menilai retensi tambahan. |
| Koleksi dan serialisasi bertahap | Koleksi besar sekitar 310 ms. Batch ini mengurangi alokasi pada validasi sambil mempertahankan snapshot transaksi, urutan JSON, dan checksum. Evaluasi streaming memerlukan fixture dengan aset besar serta pemeriksaan snapshot dan kompatibilitas. |

## Reproduksi dan batas

```powershell
npm run test:data-paths -- --capacity --output=test-results/db08.json
```

Runner memakai port 4182 dan socket Vite pengujian 4178. Jalankan terpisah
dari `test:e2e`. Untuk perbandingan, jalankan harness yang sama pada
baseline dan perubahan dengan browser serta perangkat yang sama. Waktu
bersifat pengukuran lokal. Uji Chromium memeriksa konsistensi lewat
regresi autosave dan pencadangan dari tab lama, pembaruan metadata dan
riwayat antartab, serta pemulihan cadangan ke IndexedDB kosong.
